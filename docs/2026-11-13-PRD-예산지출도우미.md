## 1. 결론 (먼저 읽을 것)

1. **KorDoc AI를 그대로 가져와(fork) 그 위에 "예산" 모듈을 더하는 방식을 권합니다.** 처음부터 다시 만들면 공문 파싱(HWP·HWPX·PDF·OCR), 한글 편집기, AI 연결, 폐쇄망 보안, 설정 화면을 모두 새로 짜야 합니다. KorDoc AI는 이 기능이 이미 동작하므로, 새로 만들 것은 **예산 과목 관리 · 공문→예산 항목 추천 · 집행 반영 · 잔액 계산** 네 가지로 줄어듭니다.
2. 라이선스는 MIT라 복제·수정·재배포가 허용됩니다. 단, **저작권 고지(LICENSE·NOTICE·THIRD_PARTY_NOTICES)를 그대로 유지**해야 하고, 앱 이름·로고는 바꾸는 것이 안전합니다(상표·혼동 문제, 아래 9장).
3. 메뉴·스타일·설정은 KorDoc AI 것을 그대로 쓰고, 왼쪽 메뉴에 **"예산" 묶음(지출 도우미 · 예산 현황 · 지출 대장)** 과 설정에 **"예산과 회계" 구획** 하나만 더합니다.
4. 이 프로그램은 **K-에듀파인 등 공식 회계 시스템을 대신하지 않는 보조 도구**로 정의합니다. 잔액은 "업무 참고용 추정치"이며, 공식 집행·결산은 기관 회계 시스템에서 합니다.

## 3. 구축 방식 비교

| 안 | 내용 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- | --- |
| A. 최소 변경 | KorDoc AI 그대로 쓰고, 예산은 엑셀 + AI 대화 프롬프트로 처리 | 개발 없음 | 잔액 자동 계산·이력 관리 불가 | 시범용 |
| **B. fork + 예산 모듈 추가 (추천)** | 저장소를 가져와 메뉴 3개·설정 1구획·RPC 영역 1개 추가 | 문서 파싱·AI·보안 재사용, 화면 일관성 | 원본 업데이트를 따라가는 병합 부담 | **추천** |
| C. 새로 개발 | 웹앱(예: 서버형)으로 처음부터 | 기관 서버 다중 사용자 가능 | HWP 파싱·편집기·폐쇄망을 다시 구현, 기간·비용 큼 | 장기 과제 |

**추천 이유**: 사용자가 원하는 것이 "KorDoc AI의 스타일·기능·설정을 그대로 유지"이므로 B가 요구와 가장 가깝고 위험이 작습니다. 예산 모듈은 `node-sidecar/src/core/budget/`와 `src/components/budget/`로 따로 두어, 원본 KorDoc AI를 업데이트할 때 충돌을 줄입니다.

## 4. 사용자와 핵심 시나리오

- **주 사용자**: 학교·교육지원청 행정실 회계 담당자(지출 담당), 사업 담당 교사·주무관
- **보조 사용자**: 행정실장(잔액·집행률 확인)

### 대표 시나리오: "공문 한 건 → 예산 반영"

1. 접수함에 받은 공문(HWPX)을 끌어다 놓는다. (기존 기능)
2. 줄 끝 **지출 도우미로** 단추를 누른다.
3. 지출 도우미가 공문에서 **금액·지출 목적·기간·거래 성격(임차/구입/여비/수당 등)** 을 뽑아 보여 준다. 확실하지 않은 값은 노란색.
4. 오른쪽에 **추천 예산 항목 3개**가 근거(일치한 낱말, 잔액 충분 여부)와 함께 뜬다. 맞지 않으면 **과목표에서 직접 찾기**.
5. 항목을 고르면 **반영 전/후 잔액**이 막대로 보이고, 잔액이 모자라거나 집행률이 경고 기준(기본 90%)을 넘으면 알린다.
6. **품의(집행 예정)로 반영** 또는 **지출 완료로 반영**을 누르고, 한 번 더 확인하면 지출 대장에 기록되고 예산 현황 잔액이 바뀐다.
7. 잘못 넣었으면 대장에서 **반영 취소**. 기록을 지우지 않고 "취소" 줄을 새로 남긴다(감사 추적).

## 6. 데이터 모델 (초안)

```ts
// 회계연도마다 파일 하나: <앱데이터>/budget/<연도>.json
interface BudgetBook {
  year: number;
  accountType: "school" | "edu_special" | "other";
  items: BudgetItem[];
  ledger: LedgerEntry[];
  importedFrom?: { file: string; at: string; sha256: string };
}

interface BudgetItem {
  id: string;            // 과목 코드 또는 생성 id
  program: string;       // 정책사업
  unit: string;          // 단위사업
  detail: string;        // 세부사업
  account: string;       // 과목(지출 항목)
  code?: string;         // 기관 과목 코드 (있으면)
  budget: number;        // 예산액(원, 정수)
  spentBefore: number;   // 불러올 때의 기집행액
  keywords: string[];    // 추천용 낱말 (자동 + 사용자 추가)
}

interface LedgerEntry {
  id: string;
  at: string;            // 기록 시각
  date: string;          // 집행(예정)일
  itemId: string;
  amount: number;        // 음수 = 취소 기록
  stage: "commit" | "paid";  // 품의(집행 예정) / 지출(집행 완료)
  docPath?: string;      // 근거 공문 (원본 경로, 원본은 고치지 않음)
  docTitle?: string;
  docNo?: string;        // 문서번호
  memo?: string;
  reverses?: string;     // 취소 대상 id
  by?: string;           // 담당자 (설정 › 내 기관 정보 이름)
}
```

**잔액 계산식**

- 집행액 = `spentBefore` + Σ(stage=paid)
- 품의 중 = Σ(stage=commit) − (지출로 넘어간 품의분)
- **가용 잔액 = 예산액 − 집행액 − 품의 중**
- 집행률 = 집행액 ÷ 예산액 (품의 포함 집행률은 따로 표시)

금액은 모두 **원 단위 정수**로 저장해 소수 오차를 막습니다.

## 8. 추천 방식

1. **거래 성격 판별(규칙)**: "임차·대절·버스" → 임차료, "구입·구매·기자재" → 물품/자산취득, "출장·여비" → 여비, "강사·수당" → 수당, "다과·회의" → 협의회비 등. 대응표는 설정에서 고침.
2. **낱말 일치(BM25)**: 공문 제목·본문과 과목의 사업명·과목명·키워드를 비교.
3. **보정**: 잔액이 이번 금액보다 적으면 감점(목록에서 빼지는 않고 "잔액 부족" 표시), 최근 같은 보낸 곳 공문에 쓴 과목은 가점.
4. **AI(선택)**: 상위 5개 후보와 공문 요약만 보내 "가장 맞는 것과 이유"를 받음. 외부 AI일 때는 기존 개인정보 가림을 거침. **AI는 고르기를 돕기만 하고, 반영은 늘 사람이 누름.**
